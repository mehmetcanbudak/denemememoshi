# Memoshi

> **Your Assistant and its team of bots, on your Mac, iPhone and iPad.**

Memoshi is a planned native app for Mac, iPhone and iPad. A personal **Assistant** runs a team of persistent **bots**, and each bot has a name, a face, a job, its own memory, its own **computer** and its own **browser**. The same bots are on every device you pair. You can talk to the Assistant and let it coordinate, or drive bots and coding sessions directly ([D109](docs/plan/decisions.md#d109)). Bots work in your projects, including writing and reviewing code. They message each other and work in groups; they read your mail and prepare drafts, and work with your calendar, reminders, contacts, notes and files; they build **Apps** that open beside the chat and change them when you ask; and you can talk to them by voice. They act on schedules and triggers inside budgets you set, and they ask before anything risky. Everything runs on your own devices by default, with your models and your keys.

The live conversation/lifecycle/Tasks foundation, mobile in-process engine, native MLS/durable device prototype, private Unix gateway, bounded installed-toolchain workflows and sealed native Python candidate exist. ## Build and test

The current build baseline is Xcode 27.2 (Swift 6.4.2) and XcodeGen 2.48.0 (from Homebrew; qualified 2026-11-20 after Homebrew moved it from 2.47.0, [canonical-ci-24](../evidence/2026-11-13-memoshi-canonical-s2/canonical-ci-24/README.md); 2.47.0 was qualified 2026-11-19, [canonical-ci-16](../evidence/2026-11-19-memoshi-canonical-ci-16/README.md)). [D97](docs/plan/decisions.md#d97) tracks newer stable Apple toolchains through qualification, rather than freezing these versions or accepting an untested floating `latest`. `scripts/ci.sh` runs 18 steps, in this order: the prerequisites, toolchain, pinned native MLS build, checked-in native MLS outputs ([`scripts/check-mls-generated.sh`](scripts/check-mls-generated.sh): the bindings, header, module map and Cargo licence inventory that the build regenerates must equal the checked-in files), pinned Pyodide runtime, release tooling contracts, spike self-tests ([`scripts/test-spikes.sh`](scripts/test-spikes.sh)), design tokens, format/lint, module boundaries, package tests, licences, schema drift, generated project, Mac/iPhone/iPad builds, app tests (the Mac and iPhone/iPad unit-test targets, [`scripts/test-apps.sh`](scripts/test-apps.sh), since 2026-11-21), sign-in flows and bundle layout. CI uses that same script on a self-hosted runner, never for fork pull requests ([D90](docs/plan/decisions.md#d90)).

**Toolchain upgrade (2026-11-01):** the installed Xcode 27.2 / Swift 6.4.2 replaces the previous 27.1 / 6.4 baseline. New stable releases are adopted by recording the version, running canonical checks and exercising affected native paths; a failed qualification stays blocked instead of silently accepting whichever version is installed. No automatic Xcode download, deployment-target change, Swift language-mode change or Pi/dependency unpinning is implied.

The native MLS build requires an existing **Rust 1.97.0** installation with the `aarch64-apple-darwin`, `aarch64-apple-ios` and `aarch64-apple-ios-sim` standard libraries. `MEMOSHI_MLS_RUST_TOOLCHAIN` selects the rustup toolchain, defaulting to `stable`. [`scripts/build-memoshi-mls.sh`](scripts/build-memoshi-mls.sh) invokes `rustc` and `cargo` through `rustup run` and rejects another compiler version or a missing target. It installs neither Rust nor its targets. Select a complete existing installation, not a selector that merely has the right name. `rustup` must already be on the shell or runner service's `PATH`. `scripts/ci.sh` appends `/opt/homebrew/bin` for XcodeGen, but does not add `$HOME/.cargo/bin`.

The Pyodide runtime under `Packages/MemoshiApp/Sources/PyodideSpike/Resources/Runtime/` is not committed. Only its `manifest.json` is, as the lock. [`scripts/package-pyodide.py --allow-download`](scripts/package-pyodide.py) recreates the runtime, wheels and licence files from pinned HTTPS sources. Every download is checked against its pinned SHA-256, and the result must match the committed manifest exactly. Existing differing bytes are refused, not overwritten. `scripts/ci.sh` runs it before the package tests. Downloads are cached in `.build/pyodide-downloads`, so later runs work offline. Run it once after a fresh clone before building the apps or package tests.

The runtime builds Pi_Swift at the tag `slice-2` (commit `ce1728ef8236d95a8b94b50a856670c48ad85365`, D134), pinned in [`scripts/lib/pi-swift-pin.sh`](scripts/lib/pi-swift-pin.sh). It needs a sibling `../Pi_Swift` **Git clone containing that commit and tag**. `scripts/check-prerequisites.sh` creates a clean checkout of the commit at `../Pi_Swift-slice-2`, which SwiftPM uses by path, and refuses one that is not exactly that commit or that holds any change, untracked file or ignored file (SwiftPM compiles ignored sources too). It uses a path because SwiftPM refuses a revision pin on slice-2: its manifest has a local package dependency. MemoshiCore's manifest must name that checkout exactly once and otherwise only the reviewed dependencies in [`scripts/lib/pi_swift_manifest.py`](scripts/lib/pi_swift_manifest.py), matched by location, so adding a dependency means adding it there; `scripts/release.py` applies the same check. It never builds the sibling's working tree. A clone without this prerequisite is not yet a self-contained release build. See [`NOTICE`](NOTICE) for Pi/transitive provenance and licences.

`scripts/check-prerequisites.sh` runs before the build and refuses a missing sibling commit or a changed checkout. For GitHub Actions, set the repository variables `MEMOSHI_PI_SWIFT_SOURCE` and, if needed, `MEMOSHI_BUILD_ROOT`. Both [CI](.github/workflows/ci.yml) and the [held release workflow](.github/workflows/release.yml) assign these variables to the job environment, overriding inherited runner values. Runner `.env` entries for those names are not the effective inputs. `MEMOSHI_PI_SWIFT_SOURCE` must name an existing local Git clone containing the pinned commit and its tag. The prerequisite script copies from that clone only when needed and never fetches a remote URL. Local runs can supply these environment variables directly.

On GitHub Actions and for release archives, the prerequisite check requires at least **15 GB free on the checkout volume**. `MEMOSHI_CI_MIN_FREE_GB` may raise, never lower, that floor. External build scratch does not bypass it. Neither workflow maps `MEMOSHI_CI_MIN_FREE_GB` or `MEMOSHI_MLS_RUST_TOOLCHAIN` from repository variables. Preserve the supported build engine, source pin and storage checks.

The canonical package runner uses `--no-parallel`: independent WasmKit/process-kill cases do not share each other's wall-clock budgets. Each scenario still exercises its own concurrent writes, tasks and cancellation; assertions and deadlines are unchanged. It also uses `--disable-automatic-resolution`, so verification cannot silently adopt newer dependencies. This functional scheduling policy is not the separate load, resource-contention or reference-hardware qualification.

`MEMOSHI_BUILD_ROOT` optionally routes SwiftPM scratch/cache and Xcode DerivedData to an existing, owned, non-symlink **0700 POSIX directory**. It does not make the host's internal temporary capacity irrelevant: on this Xcode/macOS combination, Foundation's `NSTemporaryDirectory()` still selects the internal per-user directory despite `TMPDIR`. A current build failed there with `No space left on device`; [storage evidence and constraints](docs/research/spikes/2026-11-04-s5-distribution-draft.md#4-clean-clone-ci-and-exact-source-availability) retain the exact failure. Keep the supported build engine, required storage and SDK prerequisites; external scratch is not a disk-check bypass.

## The shape of it

- **Native apps:** a Mac app on macOS 27+ (Apple silicon) and one universal iPhone and iPad app on iOS and iPadOS 27+. The interface is one SwiftUI codebase shared by the three devices, with AppKit or UIKit only where a surface needs it ([D106](docs/plan/decisions.md#d106)). v1 is for the user's own devices: a notarized Developer ID app on the Mac, and internal TestFlight or Xcode builds on iPhone and iPad, with no App Store ([D67](docs/plan/decisions.md#d67)). The reference devices are the user's own iPhone 14 Pro and iPad Pro 12.9-inch (M1) ([D80](docs/plan/decisions.md#d80)).
  - **Design:** Cognitio's design leads the shell on Mac, iPad and iPhone: card window, sidebar, transcript, composer, bot identity and editor, side panel, workbench and settings. Viticci's grammar stays for native Apple-data cards, Apps and phone navigation ([D106](docs/plan/decisions.md#d106), which supersedes [D92](docs/plan/decisions.md#d92)'s hierarchy and [D94](docs/plan/decisions.md#d94)'s preview as the lead). The look and behaviour are rebuilt in Memoshi's own code: no Kuvo- or Cognitio-derived source file, asset or string enters this repository, so the reuse [D91](docs/plan/decisions.md#d91) permits is not taken for the interface. Cognitio continues in its own repository as the behaviour reference ([D107](docs/plan/decisions.md#d107)). Builder + agents and user review, with no mandatory paid designer ([D93](docs/plan/decisions.md#d93)).
  - Later design passes, once the system is stable: Aiden-derived motion, a Grok-style roster with livelier avatars, optional Metal shader effects, generated motion and shader effects, and native 3D and Gaussian-splat views ([D115](docs/plan/decisions.md#d115)).
- **Engine:** Pi_Swift, the native Swift port of Pi, always on the latest upstream. On the Mac it runs in **memoshid**, a Swift LaunchAgent that talks to the app over JSON-RPC on a Unix socket; on iPhone and iPad it runs inside the app. No Node ships. A gate at the Phase 0 review decides it on each OS, with fallbacks. Code Mode uses the same pinned `quickjs.wasm` through `wasm2c` for shipping, with WasmKit for reference/compatibility and no JavaScriptCore, subject to parity, safety and device gates ([D89](docs/plan/decisions.md#d89)).
- **Models:** API keys, local endpoints and Sign in with ChatGPT ([D54](docs/plan/decisions.md#d54)). Claude runs through Claude Code, the unmodified program the user installs and signs in to: as the model of any bot on the Mac in Phase 1 (MOD-11) and as a coding worker in Phase 2 (R11-09). Memoshi starts no Anthropic sign-in and never reads, stores or forwards Claude credentials ([D108](docs/plan/decisions.md#d108)).
- **Assistant and teamwork:** the Assistant does small things itself and hands anything long-running or code-running to a bot through a visible Handoff. Bots message each other from Phase 1, under a grant, an 8-hop cap and budgets (GR-06). Groups of 2–6 bots with one lead arrive in Phase 2, as do Goals (GR-13): an outcome with criteria that a bot works toward hands-off, inside its budgets and the normal policy, keeping a log of each decision. Shared rooms with other people stay in v1.1 ([D109](docs/plan/decisions.md#d109)).
- **Devices:** pairing by QR code into one MLS group of your devices, then direct, relay (self-hostable, plus a hosted instance) and iCloud links, all end-to-end encrypted to that group. Every bot runs on every device: each conversation has one runner at a time under a lease, so a bot can be busy on two devices at once, with live replicas. If the runner is unreachable, side threads need an available allowed model; otherwise messages remain in a persistent, cancelable **Waiting for connection** queue. The on-device phone model stays in Drop 2 ([D88](docs/plan/decisions.md#d88)).
- **Computers:** every bot gets one, and on the Mac the user chooses it per bot ([D113](docs/plan/decisions.md#d113)): **This Mac (sandboxed)** from Phase 1; a **Bot computer**, a Linux VM per bot with a desktop and Chromium, live view, takeover and sleep when idle, at the end of Phase 2; or a **Cloud computer** (V2-02), in Phase 2 after the local ones and behind the same seam, which shows its cost before it starts (E2B by default; Orgo and Daytona selectable, [D120](docs/plan/decisions.md#d120)). GUI computer use inside a Bot or Cloud computer (R11-12) arrives with them. iPhone and iPad use the in-app environment, with typed tools and a shell front end, plus an optional emulated Linux computer through iSH. **Remote machines** (SSH; CMP-13) and an always-on Mac host (R11-07) come in Phase 3.
- **Browsers:** a WebKit profile per bot on every device; Chromium inside a Bot computer comes with it at the end of Phase 2. Watching and taking over a bot's browser or computer from iPhone and iPad (BRW-15) comes in Phase 3 ([D113](docs/plan/decisions.md#d113)).
- **Coding:** projects, sessions, review, worktrees and the terminal in Phase 2. External coding agents (Codex app-server, Claude Code and ACP agents; R11-08–R11-10) work as workers in Phase 2, on the Mac only, and every tool call still passes Memoshi policy. Team mode (CODE-18–CODE-20) is optional per project, beside direct sessions: a lead bot per piece of work in its own worktree, helper tasks that build, several reviewers merged into one verdict, and a landing gate that is a program, not a model. Before it reports done, a bot looks at what it made; that self-check (CH-38) applies to Apps, cards and page Apps from Phase 1, and to the web preview and the diff with the workbench in Phase 2 ([D110](docs/plan/decisions.md#d110)).
- **Safety:** one policy engine outside the model, with tiers T0–T5 and a permission mode per bot: **Ask first** (the default), **Auto** or **Bypass**. External actions go out as drafts except in Bypass. Secrets are used by reference only, and every decision is audited. The classes and tiers of the tools added on 2026-11-13 are [D118](docs/plan/decisions.md#d118)'s and [D121](docs/plan/decisions.md#d121)'s; [`docs/specs/policy.md`](docs/specs/policy.md) is their normative home.
- **Cards and generated interface:** native cards for Apple data and decisions, and generated interface in three layers ([D115](docs/plan/decisions.md#d115)). Layer 1 is generated cards drawn natively from a catalog of 26 SwiftUI blocks, aligned with the open A2UI standard and streamed as the model writes (CH-19, Phase 1). Layer 2 is live cards and Apps that bots write in SwiftUI-style Swift, which Memoshi's own interpreter runs under policy, with no JIT ([D68](docs/plan/decisions.md#d68); the Mac in Phase 2, iPhone and iPad in Phase 3). Layer 3 is a sandboxed web page, for page Apps, interactive artifacts and screens that connectors provide. Diagrams, charts and math are drawn natively (CH-41).
- **Apps:** the built-in ones (Mail, Calendar, Tasks, Notes, Contacts, Files) and the ones bots build share one contract ([D114](docs/plan/decisions.md#d114), [D119](docs/plan/decisions.md#d119)). An App (CH-33–CH-36) has a pane beside the chat (a side-panel tab on Mac and iPad, full screen on iPhone, or inline), in addition to sheet, window and full screen ([D85](docs/plan/decisions.md#d85)); functions it exports to the bot; view tools for the bot (`view.open`, `view.close`, `view.arrange`, `view.list`); and the user's selection in a pane travelling with the next message. Bot-written code stays sandboxed, with a permission list per version that the user approves and policy on every call. A **page App** (a sandboxed web page; CH-37) arrives in Phase 1; a **Swift App** in Phase 2 on the Mac and Phase 3 on iPhone and iPad, and one can replace a page App and keep its data. Plugin developer mode is Mac only and off by default (CH-44): compiled Swift plugins run in a separate helper process, and the user may switch a single App or plugin to "Full access on this Mac" after a typed confirmation. App background jobs, widgets and the signed bytecode cache come in Drop 1, after v1.0 ([D71](docs/plan/decisions.md#d71), [D87](docs/plan/decisions.md#d87)).
- **Mail and personal information:** typed `mail.*` tools over Gmail, Microsoft 365 and IMAP (CON-08), and Calendar, Reminders and Contacts through Apple's frameworks (AP-14). Built-in panes on the App contract: Mail, Calendar, Reminders merged with Tasks, Contacts, Notes (Markdown files) and Files with the Library; the Mac in Phase 1 (AP-15–AP-20), iPhone and iPad in Phase 3 (AP-21) ([D116](docs/plan/decisions.md#d116)). A bot prepares a mail draft and the user sends it: `mail.send` is T4 and a Draft, except where the user let that bot send mail by itself, which never applies to a run started by incoming mail or other outside content ([D57](docs/plan/decisions.md#d57)). Tidying a mailbox (`mail.organize`: archive, mark, label, move, star) is a lighter class that a standing rule can cover (SEC-28; [D118](docs/plan/decisions.md#d118)).
- **Search, connectors and media:** `web_search` and `x_search` in Phase 1 (CON-15, CON-16), with source links shown as chips; a built-in connector catalog over MCP with connect cards in Phase 1 (CON-14), and Composio as an optional extra in Phase 2, off by default (CON-19); connector event triggers on the Mac in Phase 2 (RT-14); image and video generation in Phase 2 (CON-17, CON-18) ([D112](docs/plan/decisions.md#d112)). Each capability starts with a default provider on the user's own key and can be switched ([D120](docs/plan/decisions.md#d120)).
- **Voice:** a voice session only listens and speaks; work goes to the bot's normal queue, so policy, Cards and budgets apply unchanged. Two engines, chosen per bot or per call: a cloud realtime voice (xAI by default, OpenAI selectable), where audio leaves the device and the interface says so, and an on-device engine (Apple's speech recognition and voices, plus an optional downloadable open voice) that works offline. The Mac in Phase 2 (V2-09); iPhone and iPad in Phase 3 (VO-05), with the Action Button, a Live Activity and a Start Voice Chat intent (VO-06). With it come reading a reply aloud, voice memos, voice navigation with read-back, and an optional narrator (VO-01–VO-04; [D111](docs/plan/decisions.md#d111), [D120](docs/plan/decisions.md#d120)). Dictation is unchanged.

## Conventions

- **Binding vocabulary:** Assistant, Bot, Chat, Project, Session, Group, Task, Handoff, Routine, Watch, Wake, Computer (This Mac (sandboxed), Bot computer, Cloud computer, Remote machine), Browser, Memory, Connector, Skill, Card, App (page App, Swift App), Goal, Approval, Draft, Artifact, Inbox, Budget, Grant, Permission mode (Ask first, Auto, Bypass), team mode, plugin developer mode ([MASTER_PLAN §5](docs/plan/MASTER_PLAN.md#5-vocabulary-and-object-model)).
- **Evidence:** claims cite research docs or primary sources. `[INFERENCE]` marks reasoning, and "(vendor claim)" marks unverified maker statements.
- **Decisions** change only by a new decision that supersedes an old one ([change control](docs/plan/decisions.md#change-control)).
- **Reuse:** normally copy code only from permissive sources, with attribution ([D33](docs/plan/decisions.md#d33)). The explicit exception is the GPL-3.0 iSH module ([D69](docs/plan/decisions.md#d69)), which keeps its licence. [D91](docs/plan/decisions.md#d91) permits Kuvo Code reuse for personal/noncommercial use, but that reuse is not taken for the interface: no Kuvo- or Cognitio-derived source file, asset or string enters this repository ([D106](docs/plan/decisions.md#d106)). Permissive dependencies (SwiftTerm, Textual, WhisperKit and the usage-meter library that UsageKit forks) are used from their original upstreams, not from Cognitio's forks. This grants no blanket permission to copy product artwork.
- **Kuvo and Cognitio source:** Cognitio's running app and source are read as a behaviour reference; code is not copied or translated file by file, and each surface gets a written behaviour description before it is built ([D106](docs/plan/decisions.md#d106)). Cognitio continues in its own repository under its own licence, and Memoshi's agents do not edit it ([D107](docs/plan/decisions.md#d107)). Third-party captures and personal data stay outside the repositories. Source access does not select a fork or change Pi_Swift. O13 stays open: nothing built under D106 may close a public or paid release.
- **Research matrix:** regenerate it after editing a product profile with `python3 docs/research/agentic-workspace-landscape/_matrix.py`.
