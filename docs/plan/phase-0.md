**Stop rule.**
- **Q1, Q2 or Q3 fails on macOS:** D46's Mac fallback applies: memoshid goes back to upstream Pi in bundled Node, as D6, D12, D13 and D15 read on 2026-10-20. Phase 1 starts once that path passes its own S1 and S5 checks; the gate review sizes the delay [INFERENCE: one to two weeks].
- **Q1, Q2 or Q3 fails on iOS:** D46's iOS fallback applies: v1's iPhone and iPad app becomes a remote screen for Mac bots, and running bots on the phone or tablet moves to v1.1. Phase 1 (Mac first) starts as planned; the gate records the Phase 3 changes.
- **Q7 fails:** Phase 1 does not start until the ship path works.
- **Q4 fails:** Phase 1 starts, because it runs on one device. The gate records which link or lease measurement failed, sets O10 from what passed, and changes the Phase 3 plan; a link that fails leaves the others to carry the away path ([D48](decisions.md#d48)).
- **Q5 fails:** Phase 1 starts with foreground-only WebKit browsing on This Mac; background browsing waits for Chromium with Bot computers at the end of Phase 2 ([D113](decisions.md#d113)).
- **Q6 fails:** S4's fallbacks apply in [D77](decisions.md#d77)'s fixed order ([S4](#s4)), each used only after it passes the full S4 escape suite with 0 escapes.
  - If none passes, Phase 1 still starts, but every ticket that runs bot commands or file tools (CMP-03 and the work built on it) waits until one does, and the gate takes a new decision on [D16](decisions.md#d16).
- **Q9 fails:** Phase 1 starts, because Python on iPhone and iPad is Phase 3 work. [D79](decisions.md#d79)'s fallback order applies ([S6](#s6)): a trimmed, lazily loaded Pyodide; then the Mac's Python for phones; native CPython in the style of Carnets [INFERENCE] only if both fail. The S6 report sizes the step the gate takes, and the gate records the Phase 3 change. If S6 was cut, it runs in Phase 2 week 1 (W52) instead ([§10](#cut-list)).
- **Demo:** a failed spike's demo steps switch to the variants in [§8](#exit-demo) ([risks R26, R27](risks.md#3-risk-register)).
- **Later probes:** the Swift engine probe (W52) and the iSH probe (W135) are not Phase 0 questions ([D122](decisions.md#d122)'s estimated calendar); their fallbacks are in [10-roadmap §13](10-roadmap.md#13-what-could-change-the-plan).

## 2. Repo layout

This repo holds the plan and native code ([D36](decisions.md#d36)). The seven current SwiftPM packages are under `Packages/`; the tree describes implemented source, not complete domain qualification. Domain responsibilities follow [04-architecture.md](04-architecture.md). No TypeScript runtime ships. `MemoshiRuntime` owns the Pi adapter against the exact committed consumer development candidate documented in [HANDOFF](../HANDOFF.md#text-chat-development-proof); qualifying S1/slice and shipping gates remain separate ([D44](decisions.md#d44), [D46](decisions.md#d46), [D90](decisions.md#d90)).

```
Memoshi/                              this repo
├── apps/
│   ├── mac/
│   │   ├── project.yml               XcodeGen spec for every target; the Xcode project is generated, not committed
│   │   ├── Memoshi/                  Mac app target: entry point, menu bar extra, Info.plist, entitlements
│   │   │   └── Resources/LaunchAgents/   memoshid agent plist (label per 09-platform-macos.md)
│   │   └── Tests/                    UI snapshot harness, performance harness
│   └── ios/
│       └── MemoshiMobile/            universal app, in-process engine, native/browser/Python review; physical background qualification open
├── memoshid/                         main.swift: real executable over MemoshiDaemon; app-shaped helper in the Mac bundle
├── Packages/                         current local SwiftPM packages; each owns its tests
│   ├── MemoshiProtocol/              Swift wire types/catalogs, schema generator and fixtures contract (D78)
│   ├── MemoshiCore/                  metadata Store, Pi runtime/lifecycle/children, D96 sandbox and authenticated egress qualification
│   ├── MemoshiIPC/                   same-FD transport (NIO 2.104.0); MemoshiDevice/Apple native MLS and durable prototype state
│   ├── MemoshiMLS/                   pinned native MLS bridge, generated bindings, vendor/provenance checks
│   ├── MemoshiDaemon/                helper/replay, development conversation/model/task/folder/broker RPCs and qualification runners
│   ├── MemoshiClient/                typed Mac client, reconnect/replay, explicit application receipts and bootstrap
│   └── MemoshiApp/                   AppCore, DesignSystem, conversations/shell, native pairing and offline PyodideSpike targets
├── protocol/                         protocol.schema.json, generated from MemoshiProtocol and committed, and fixtures/, both for tests and docs (D78)
├── relay/                            the self-hostable relay; a prototype in S2
├── spikes/                           throwaway spike code, one folder per spike; deleted or promoted at the gate
├── scripts/                          dev, sign, notarize, ledger server, smoke, chaos
├── docs/                             plan, specs, research (spike reports go to docs/research/spikes/)
└── NOTICE                            source/dependency provenance and applicable notices; not a blanket permissive licence
```

The selected eventual user layout remains `~/Library/Application Support/Memoshi/`, per [04-architecture.md](04-architecture.md). The Mac development text profile deliberately uses the separate `~/Library/Application Support/Memoshi Development/Text Chat`: metadata `memoshi.sqlite`, actual Pi SQLite entries per conversation, and private `run/` with socket/token/lock. The default infrastructure-only daemon opens no Pi runtime. The implemented iPhone/iPad engine keeps stores inside its container without a socket; physical background qualification and distributed lease authority remain open. Normal app/helper composition still disables tools, MCP, Code Mode, environments and subagents. Never alter or reuse prototype data to make a smoke pass; the [current proof](../HANDOFF.md#text-chat-development-proof) records an isolated native root, not a prototype migration.

**Rules, enforced in CI from week 1:**

1. Only the runtime module in `MemoshiCore` imports Pi_Swift modules ([D44](decisions.md#d44)); a lint rule fails the build otherwise.
2. The Swift types in `MemoshiProtocol` are the single source of truth for wire shapes ([D78](decisions.md#d78)). `protocol/protocol.schema.json` is generated from them and committed for fixtures and docs; a drift check fails CI when the committed schema and the types disagree. Hand-copied models, which drifted in Draft 3, are not allowed.
3. The apps speak to memoshid only through the protocol, and never import its executable target; memoshid runs headless in tests.
4. Pi_Swift is pinned to an exact commit (`Package.resolved` is committed); moving the pin needs a green contract suite ([D44](decisions.md#d44)).
5. A build check fails if a product build contains Pi_Swift's Anthropic, Google, Meta or Codex-client-ID sign-in flows; Sign in with ChatGPT, API keys, and OpenRouter's and Radius's sign-ins, which create usage-billed keys and reuse no subscription, stay ([D54](decisions.md#d54), [D79](decisions.md#d79); Pi_Swift requirement E11). This is catalog row DIST-03, which [D108](decisions.md#d108) narrows to "no Anthropic sign-in flow inside the app": Claude on a plan is reached only through Claude Code, which the user installs and signs in to outside Memoshi, and Memoshi ships no Anthropic client ID. Implemented on 2026-11-03 by `scripts/check-signin-flows.sh`, which runs after the app builds and is tied to candidate `892585f`: it fails when a manifest enables Pi traits or a built binary carries a restricted client ID.
6. Every copied or ported file carries a provenance header; `NOTICE` and the third-party register retain the applicable terms and required notices. Any selected Kuvo reuse retains PolyForm Noncommercial 1.0.0 coverage, with the upstream revision, paths and changes recorded ([D33](decisions.md#d33), amended by [D91](decisions.md#d91)). [D106](decisions.md#d106) selects none for the interface: no Kuvo- or Cognitio-derived source file, asset or string enters this repository. The current licence scan checks dependencies, not vendored-source provenance or compatibility; before a chosen import is consumed, update its licence/provenance records and enforcement for that actual scope, without a blanket PolyForm allowlist.

**Toolchain.** Current baseline: Xcode 27.2 with its macOS/iOS SDKs and Swift 6.4.2 in strict-concurrency mode ([D97](decisions.md#d97), [09-platform-macos.md](09-platform-macos.md)). Track new stable Apple toolchains through recorded qualification, not a permanently frozen release or untested floating `latest`; canonical CI and affected native smoke gate each upgrade. Deployment targets stay macOS 27.0 (arm64 only) and iOS/iPadOS 27.0, with no availability fallbacks ([D31](decisions.md#d31), [D56](decisions.md#d56)). SwiftPM's 6.4 tools minimum is unchanged. No Node, pnpm or Zod.

### 2.1 XcodeGen, not Tuist

| Criterion | XcodeGen | Tuist |
|---|---|---|
| License and status | MIT; 2.46.0 released 2026-07-16; pushed 2026-10-13 ([repo](https://github.com/yonaskolb/XcodeGen)) | CLI MIT; `server/` and two other directories MPL-2.0 ([license](https://github.com/tuist/tuist/blob/main/LICENSE.md)) |
| Manifest | One YAML file | Swift manifests |
| What we need it to do | The Mac app, memoshid and the iPhone and iPad targets, entitlements, embedded resources (memoshid, the LaunchAgent plist, provisioning profiles), schemes | Same |
| What else it offers | Nothing we need | Binary caching (through a Tuist server), module-graph rules, generated accessors: valuable for many targets |
| Continuity | Draft 3's working `project.yml` ports directly | New |

**Decision: XcodeGen.** Features live in local SwiftPM packages, so the generated project only wires the targets and their embedded payloads; generating instead of committing the project keeps entitlements and build phases reviewable as text. Revisit at the Phase 3 gate, when the iPhone and iPad app grows.

## 3. One builder, capacity and calendar

One person builds Memoshi with coding agents ([D45](decisions.md#d45), amended by [D93](decisions.md#d93)); the hats APP, NAT, RT, PD and QA are lanes of work, not people ([10-roadmap §4](10-roadmap.md#staffing)). The builder and agents deliver the tokens, components and avatar prototype against user-approved references, with user design review and required design QA. Targeted external artwork, accessibility or polish help is optional only for a concrete identified gap with separately approved scope and cost; there is no hiring or payment dependency and no assumed saving in builder days. Builders and observers may inspect Kuvo's GitHub source under [D91](decisions.md#d91) and read Cognitio's running app and source as a behaviour reference, with no mandatory separate observer; neither is copied into this repository ([D106](decisions.md#d106)). The Pi_Swift engine work (the product slice up to slice-ready, the store lock, the iOS host adapter) runs in the Pi_Swift repository with its own agent; Memoshi's Phase 0 integrates and measures it.

## 5. Spikes

**Rules for every spike:**

- **Timebox.** A question still open at the end of its timebox counts as a fail for that question and is reported as such. An extension is paid for with an item from the [cut list](#cut-list).
- **Evidence.** Raw measurements (CSV, with n, p50 and p95, hardware, OS build) go into the report, not only the outcome.
- **Outcomes.** Every measurement is **pass**, **marginal** or **fail**.
  - **Marginal** means the value lies between the pass and fail bounds, or meets a "passes only with" condition.
  - A marginal result does not stop the gate by itself. It gets an owner and a Phase 1 ticket to reach the pass bound, and it is re-measured at M1, the Phase 1 gate. There it must pass, or its spike's fallback applies.
  - Rows whose pass and fail bounds meet (counts that must be 0 or 100%) have no marginal band.
- **Report.** `docs/research/spikes/Sn-<name>.md`: questions with answers and evidence; measurements; the outcome table (pass, marginal, fail); proposed decision updates; Phase 1 tickets; what happens to the spike code; risks re-scored.
- **Code.** Spike code lives in `spikes/Sn-*`. It reaches production only through normal review.
- **Secrets.** Real API keys come only through the Keychain broker (P0-20). Until it lands in week 2, S1 runs on the local OpenAI-compatible endpoint, which needs no key. Canary secrets are planted in every run.

## 8. Exit demo script

About 14 minutes, on the reference box and the iPhone 14 Pro, from a notarized DMG and an internal TestFlight build. Before the demo: one provider API key added through the "add model key" sheet (stored in Keychain), a test project folder granted to a test bot, the effect-ledger server running, a GitHub-style MCP server configured, the iPhone signed in to the same iCloud account, and canary secrets planted. RPC and event names are from [protocol.md](../specs/protocol.md) and [events.md](../specs/events.md).

1. **Install and launch.** Open the DMG on the clean machine; first launch shows no Gatekeeper warning. The app registers memoshid with `SMAppService`; the menu bar extra shows memoshid running. *(S5)*
2. **Connect.** The app reads `run/memoshid.token`, sends `system.hello`, passes both peer checks, and calls `events.subscribe {after: 0}`. The debug HUD shows the protocol version and the current `seq`. *(S5)*
3. **Talk to the Assistant.** Send "What can you do today?" with `chats.send`. The reply streams from the real model with the streaming text and thinking indicator; the HUD shows time to first token and memoshid overhead. *(S1, design)*
4. **Edit identity live.** Change the Assistant's display name and one persona line in its record. The next reply uses both, with no restart. *(S1.4)*
5. **Approval under policy.** Ask a test bot in Ask first to write a note in its home and run `ls` on its granted folder. An approval Card enters; choose Allow once (`cards.respond`). The command runs in the This Mac sandbox. The bot then tries to read `~/.ssh/id_ed25519`: denied, audited, and reported to the model as a structured denial. *(S1.10, S4)*
6. **Code Mode and MCP.** Ask the bot to "summarize the five newest issues". It finds the MCP tools through `tool_search` and runs a Code Mode script with five nested calls. The policy view lists each nested call with its parent. *(S1.8–S1.10)*
7. **Subagent.** The bot hands a side question to a persistent background subagent; the Tasks stub shows the child task and its answer returns as a follow-up. *(S1.7)*
8. **Kill the brain.** Start a task that posts to the effect-ledger server and then waits on a second approval. From the debug menu, kill -9 memoshid. launchd restarts it; the app reconnects and replays from `after`; the pending approval Card is still there. Approve it. The run finishes, and the ledger shows each effect exactly once. *(S1.11, S1.13, S5.7)*
9. **The iPhone.** On the internal TestFlight build, talk to a bot that runs on the phone. Swipe the app away mid-turn during its continued-processing task, relaunch, and watch the turn resume; an App Intent's attempt to open the same store is refused. *(S1.18, S5.10)*
10. **Pair and hand over.** Pair the iPhone with the Mac by QR code. Message a bot from the iPhone while the Mac runs its Chat: the answer streams from the Mac, and the lease stays there. Make the Mac unreachable, and the Chat's lease moves to the iPhone; reconnect it, and the idle Chat's lease returns to the Mac. The Mac shows the live replica, and a write with the stale epoch is rejected. Turn the relay off and decide an approval on the phone through iCloud. *(S2)*
11. **Browse with the windows closed.** The bot opens a test site in its own WebKit profile; a sign-in Card fills the credential, and the transcript shows no secret. Close every window. The bot finishes a scripted browse; reopen and show the result and its snapshot. *(S3)*
12. **Gallery.** Tokens in light, dark and Increase Contrast; motion primitives with Reduce Motion on and off; the avatar grid in all eight statuses; the P-STREAM numbers from the harness. *(design)*
13. **Audit and scoreboard.** The audit list shows allowed, denied, approved and nested calls on both devices; a grep for the canary secrets across logs, transcripts and diagnostics returns nothing; the spike scoreboard shows pass, marginal or fail for every measurement, and the D46 gate result.

**Fallback variants.** When a spike failed and the gate recorded its fallback ([§1](#1-what-phase-0-must-prove)), its steps change. The scoreboard shows the failed measurements beside the fallback's results.
- **S1 failed on iOS:** step 9 shows the remote-screen fallback: the iPhone follows and approves a Mac bot instead of running its own.
- **S2 failed for one link:** step 10 runs on the links that passed; a failed lease measurement shows hand-over of an idle conversation only.
- **S3 failed:** step 11 runs with the window open, as foreground-only browsing. Closing the window pauses the browse, as the fallback says.
- **S4 failed:** step 5 runs in the first fallback in [D77](decisions.md#d77)'s order that passed the full S4 escape suite with 0 escapes. If none passed, step 5 shows the hold instead: the bot's command waits, and its Card says commands are held until a safe computer exists.

**The line to land:** close the window, kill the brain, pick the bot up on your phone, and the team keeps its word: nothing runs twice, and nothing risky runs without you.
