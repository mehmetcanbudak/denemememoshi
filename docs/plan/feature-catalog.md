## How to read this

### Phases

Phases follow [MASTER_PLAN §12](MASTER_PLAN.md#12-roadmap-at-a-glance). **v1.0 = Phases 0–4.** Drop 1 (D1) and Drop 2 (D2) follow it as gated stages before v1.1; their rows carry D1 or D2 in the Ph column ([D87](decisions.md#d87)). Milestones name the gates ([D117](decisions.md#d117)): **M1** is the gate at the end of Phase 1, **M2** at the end of Phase 2 and **M3** at the end of Phase 4, and **v1.0 = M3 passed**. "Phase N" says when work happens; M1, M2 and M3 name gates. Phase 0 and its gate on Fri 2026-11-27 are unchanged. The Weeks and gate dates below are [D122](decisions.md#d122)'s calendar, which supersedes [D87](decisions.md#d87)'s; every duration is an [INFERENCE] estimate for one builder with coding agents ([D45](decisions.md#d45)), and [10-roadmap.md](10-roadmap.md) carries the item-by-item sizing. Where D106–D117 say "in M1", "in M2" or "in M3", read Phase 1, Phase 2 and Phase 3 ([D122](decisions.md#d122)).

In the R11 and V2 tables, priority is relative to that release, except for the rows that [D109](decisions.md#d109)–[D117](decisions.md#d117) moved into v1.0 on 2026-11-13: those were re-set against their v1.0 phase, P0 when a milestone exit criterion in [amendment §3](AMENDMENT_2026-11-13.md#3-milestones) depends on the row and P1 otherwise. Rows added on 2026-11-13 follow the same rule, with P2 for optional items.

### IDs and columns

- IDs are `PREFIX-NN`, stable, never renumbered and never reused. A dropped feature stays in its table marked **Retired**, with the reason and no phase or priority; retired rows are excluded from counts. A new feature takes the next free number in its domain.
- A row marked **Deferred** is out of v1 until a public release, which is decided after v1.0 (O13, [D67](decisions.md#d67)). It keeps its ID and scope, has no phase or priority, and is excluded from counts like a retired row.
- A row that a decision moves stays in its table and keeps its ID: its Ph cell changes and its Scope ends with a "(moved from … by Dnnn)" note.
- The roadmap, specs, tests and gate reviews cite these IDs. The [phase index](#phase-index) lists them per phase and drop.
- **Done when** is the acceptance test. Timings are measured on the baseline test Mac named in [09-platform-macos.md](09-platform-macos.md). Targets marked [INFERENCE] are our estimates, confirmed or changed at the phase gate.
- **Draft 3** is the Draft 3 catalog ID the row adapts; "build" means ported Draft 3 code ([D36](decisions.md#d36)); "new" means no Draft 3 row.
- Spike rows in Phase 0 (S1–S5) are owned by [phase-0.md](phase-0.md); their "done when" is the spike's answer, not a shipped feature.

### Cross-cutting rules

Adapted from Draft 3 Part I "Apple platform integration" rules and extended:

1. Apple services are optional at runtime. Every feature that uses one has a deterministic fallback ([D41](decisions.md#d41)).
2. App Intents, notifications, widgets and the menu bar never bypass policy. They render decisions made in memoshid ([D9](decisions.md#d9)).
3. Foundation Models never approve, execute or change permissions ([D10](decisions.md#d10)).
4. Spotlight and widgets read a local snapshot; they never index transcripts or code by default.
5. A feature that adds a sidebar section must be a first-class object ([principle 12](MASTER_PLAN.md#3-principles)).

# Part VI: Definition of done for v1.0

Adapted from Draft 3 Part IV. v1.0 is M3 passed ([D117](decisions.md#d117)): it ships when all of the following hold, with evidence at the M1, M2 and M3 gate reviews; M3, at the end of Phase 4, is the v1.0 gate, estimated for Fri 2030-09-27 ([D122](decisions.md#d122); [10-roadmap.md](10-roadmap.md)). Items 21–25 were added on 2026-11-13 from the milestone exits in [amendment §3](AMENDMENT_2026-11-13.md#3-milestones). Metric targets are from [MASTER_PLAN §14](MASTER_PLAN.md#14-success-metrics); measurement methods are in [01-product.md](01-product.md#6-success-metrics).

1. **First launch to value.** A new user names the Assistant, connects a model, meets the starter team and gets a useful result within 10 minutes in moderated first-run sessions; the ≥ 60% cohort target waits for a public release (O13, [D67](decisions.md#d67)). ON-01–ON-05, AS-04.
2. **Builder activation.** A builder opens a repo, asks for a change, reviews it with line comments and accepts a diff within 10 minutes of opening the project, in timed sessions with builders new to Memoshi; the ≥ 50% cohort target waits for a public release (O13). PR-01, CODE-01–CODE-07.
3. **Durability.** memoshid (Mac) or the app (iPhone and iPad) can be killed mid-task, including mid Code Mode script and mid cross-device call, and resumes in ≥ 99% of runs with zero duplicated external side effects. CH-01, CH-05, CH-11, IOS-02, DEV-06.
4. **Safety.** In Ask first and Auto bots, no T4 or T5 action runs without a draft or approval; in any mode, no money or credential action runs without a card; this holds in the red-team suite and opt-in telemetry. Triggers and other bots never escalate without an attended user decision; the audit log is hash-chained; one switch stops every bot. SEC-01–SEC-17, SEC-20, SEC-22–SEC-25, SEC-27, SEC-28, CON-13.
5. **Proactivity.** A routine runs for a week with the app windows closed, stays within its budget, and notifies without news in ≤ 10% of runs; watches spend zero model tokens between changes. RT-01–RT-12, BU-03–BU-05, BU-07.
6. **The Assistant delegates.** The Assistant does small things itself and hands anything long-running or code-running to a bot with a Handoff, and reports back with evidence ([D109](decisions.md#d109)). AS-08, GR-04.
7. **Devices.** Every bot is usable from Mac, iPhone and iPad with one history; 100 runner hand-overs give no split history and no duplicated effect; on the reference iPhone with no connectivity or available model, queued messages survive restart with their original `requestId`, can be canceled before delivery, execute nothing while queued and reach the current confirmed runner exactly once after reconnect under current grants, budgets and recovery holds. A real side thread is tested separately with an available allowed model and rejoins once with its model-written summary and exact recorded effect list; approvals reach a phone away from home over the relay and over iCloud ([D88](decisions.md#d88)). DEV-01–DEV-11, IOS-01–IOS-04.
8. **Computers.** Every Mac bot defaults to This Mac (sandboxed), and every iPhone and iPad bot to the in-app environment; the optional iSH computer on iPhone and iPad runs app commands as real programs under policy. On the Mac the user chooses per bot between This Mac (sandboxed), a Bot computer and a Cloud computer, and a bot finishes a web chore in its own computer while watched; a bot's computer can be watched and taken over from the phone; a bot runs on a Mac mini while the laptop sleeps ([D113](decisions.md#d113)). CMP-03, CMP-06–CMP-14, IOS-03, IOS-06, BRW-11, BRW-12, BRW-15, V2-02, R11-07, R11-12.
9. **Browsers.** Each bot keeps its own logins; sign-in cards fill credentials the model never sees; takeover and hand back work on WebKit on every device, and from iPhone and iPad for a browser another device hosts. BRW-02–BRW-08, BRW-13, BRW-15.
10. **Memory.** Every entry has provenance; user and team writes are proposals; the nightly consolidation diff is reviewable and undoable. MEM-01–MEM-10.
11. **Cost.** No overrun beyond one in-flight model call per runner, held by budget slices ([D76](decisions.md#d76)); every routine shows a cost preview before it is enabled. BU-01, BU-03–BU-05, BU-07, RT-12.
12. **Engine range.** Code Mode and MCP work together in one conversation, and policy sees every nested call. The pinned upstream `quickjs.wasm` ships through wasm2c only after upstream-oracle differential parity and the integrated physical-device, policy and recovery gates; WasmKit remains the reference and compatibility fallback, with no JavaScriptCore backend ([D89](decisions.md#d89)). CH-05, CON-01, SEC-01.
13. **Portability.** A bot round-trips through `bot.md`; the full data export is complete. EXP-01, EXP-02, EXP-06.
14. **Quality.** WCAG 2.2 AA passes; every §14 responsiveness target is met; crash-free sessions ≥ 99.5%. SH-18, SH-19.
15. **Ship path.** The Mac app is Developer ID signed with a G2 certificate, notarized and updated by Sparkle, with memoshid surviving updates; the iPhone and iPad app installs on the user's own devices from internal TestFlight builds that CI keeps fresh, with no App Review in v1 ([D67](decisions.md#d67)); compliance checks are green, and GPL code stays in the iSH module ([D69](decisions.md#d69)). DIST-01–DIST-05, DIST-08.
16. **Privacy.** Telemetry is off by default and opt-in payloads contain no content. SEC-16, SEC-17.
17. **Design.** Scenario-based user review and design QA pass for accepted personal-resource, delegation, project-review and App journeys across relevant Mac/iPhone/iPad devices and states, following Cognitio's design for the shell on every device, rebuilt in Memoshi's own code as one SwiftUI codebase, with Viticci's grammar for native Apple-data cards, Apps and phone navigation ([D106](decisions.md#d106)); no Kuvo- or Cognitio-derived source file, asset or string is in the repository (DIST-03). Same-state visual comparisons and measurements support judgments of usability, consistent semantic tokens, honest state/actions, VoiceOver, keyboard access, Dynamic Type, Reduce Motion and contrast, not exact competitor screenshot scores. The motion inventory ships with Reduce Motion parity and within frame budgets; Liquid Glass stays in chrome; all existing design QA/accessibility/performance checks remain ([03-design-system.md](03-design-system.md)). Draft 3's "looks and feels like Kuvo" and [D92](decisions.md#d92)'s Viticci-led hierarchy are history, not current visual gates. SH-04, SH-05, AP-01.
18. **Apple platform.** Notifications are actionable, dictation is on-device, Foundation Models jobs fall back cleanly, App Intents never bypass policy, and the Apple tool catalog works on every device it lists; none of them is a hard dependency. AP-02–AP-05, AP-09–AP-11, AP-14.
19. **Cards and Apps.** Native and generated cards render on every device, and catalog cards draw as they stream; bots build page Apps, and write live cards and Swift Apps in SwiftUI-style Swift, which each device compiles locally and Memoshi's Swift engine runs with no JIT under time and memory limits. Apps open as a pane beside the chat (a side-panel tab on Mac and iPad, full screen on iPhone), or on the Mac as a sheet over their conversation, with Open in Window, Full Screen and a per-App preference ([D85](decisions.md#d85), [D114](decisions.md#d114)). A bot builds a working pane in one conversation and changes it on request, and a Swift App replaces a page App and keeps its data. Unsupported code fails at compile time with a fixable error; an App keeps its data across relaunches; a program calls only what its approved permission list names, and every card and App action passes policy. The signed bytecode cache and other App power features remain Drop 1 ([D87](decisions.md#d87)). CH-09, CH-19–CH-25, CH-31, CH-33–CH-45, TP-07.
20. **Python and notebooks.** Bots run Python with NumPy, pandas, SciPy and Matplotlib in their sandbox on the Mac and in the in-app environment on iPhone and iPad, and long runs go to the Mac; notebooks open, change and run in the native view on the Mac; every Python run and package install passes policy. PY-01–PY-03.
21. **Personal information.** Mail (Gmail, Microsoft 365 and IMAP), Calendar, Reminders with Tasks, Contacts, Notes and Files with the Library each have a built-in pane on Mac, iPhone and iPad; inbox triage and the week view are used daily; a bot prepares mail as a Draft and the user sends it, except where the user let that bot send mail by itself; tidying a mailbox runs under `mail.organize` and its standing rules ([D116](decisions.md#d116), [D118](decisions.md#d118)). CON-08, CON-20, SEC-28, AP-14–AP-21.
22. **Teamwork.** With the grant, bots message each other inside the 8-hop cap and their budgets; Groups of 2–6 with one lead keep the round and hop caps and their group budget; a Goal runs hands-off inside its budgets and logs each decision ([D109](decisions.md#d109)). GR-01–GR-03, GR-05–GR-07, GR-09–GR-11, GR-13.
23. **Engineering team.** Codex, Claude Code and ACP agents work as coding workers on the Mac with every tool call under Memoshi policy; a team-mode change lands only after its checks pass ([D110](decisions.md#d110)). R11-08–R11-10, R11-15, CODE-18–CODE-20.
24. **Voice.** A call hands work to a bot and speaks the result, on the cloud realtime engine and on the on-device engine, on Mac, iPhone and iPad; a call starts from the Action Button ([D111](decisions.md#d111)). V2-09, VO-01–VO-06.
25. **Reach.** `web_search` and `x_search` return results with source chips; a catalog connector connects from its card; images and video are generated on the user's provider key; Claude answers through Claude Code on the Mac with no Anthropic sign-in inside the app ([D108](decisions.md#d108), [D112](decisions.md#d112)). CON-14–CON-19, RT-14, MOD-11.

**The drops.** Drop 1 and Drop 2 each ship when every one of their rows' Done when holds, with evidence at their own gate review ([D87](decisions.md#d87)): Drop 1, CH-26–CH-30 and CH-32; Drop 2, AS-10, CODE-17, TP-10, BRW-14, MOD-09, AP-12, AP-13 and PY-05. CH-31 and BRW-15 left the drops for Phases 2 and 3 on 2026-11-13 ([D113](decisions.md#d113), [D114](decisions.md#d114)).

## Open questions

1. **VM image source (Phase 2, [D113](decisions.md#d113)).** CMP-07 needs a signed image. Is it downloaded next to app updates, or built on-device from a signed recipe?
2. **Mail connector.** Resolved 2026-11-13 by [D116](decisions.md#d116): typed `mail.*` tools over Gmail, Microsoft 365 and IMAP replace the connector (CON-08); MCP mail connectors stay possible.
3. **AP-08 Calendar and Reminders.** Resolved 2026-10-22: folded into the Apple tool catalog (AP-10, AP-11; [D50](decisions.md#d50)).
4. **Cost preview before history.** BU-04 estimates from past runs; a new routine has none. Is RT-07's "Try once" trial the required first data point?
5. **Phase 1 load.** Phase 1 holds about half of v1.0's rows, now including single-bot Handoffs, bot-to-bot messages, page Apps, mail and the built-in panes. Which P1 rows move to Phase 2 if the M1 gate slips? The cut order in [10-roadmap.md](10-roadmap.md) decides.
6. **Claude Code as a model (MOD-11).** [D108](decisions.md#d108) does not say how Memoshi's tools, Cards and policy reach a turn relayed through Claude Code; R11-09 names Claude Code's permission protocol for the worker role only. Spec review.
7. **Action Button device (VO-06).** The reference iPhone 14 Pro ([D80](decisions.md#d80)) has no Action Button [INFERENCE: platform knowledge], and the M3 exit asks for a voice call from it. Which device proves it?
8. **Tasks in two places.** IN-08's global Tasks view and AP-17's Reminders and Tasks pane both list Tasks. Are they one list shown twice? Design review.
9. **Two developer modes.** Resolved 2026-11-13: [D114](decisions.md#d114)'s Mac-only setting for compiled plugins is written "plugin developer mode" (CH-44); the Guided/Developer interface level (SH-12) keeps its name.
10. **Library before projects (TP-08).** [Amendment §4.6](AMENDMENT_2026-11-13.md#46-personal-information-d116) lists TP-08 beside the Phase 1 Files and Library pane. This catalog keeps TP-08 in Phase 2, because its project Artifacts tab needs PR-01, and lets AP-20 show the bot's Library in Phase 1. Should TP-08 be split?
11. **Hop cap before Groups.** GR-06 needs the 8-hop cap in Phase 1, while GR-05, which owns the caps, moved to Phase 2 with Groups ([D109](decisions.md#d109)). GR-06 now carries the hop cap from Phase 1; should GR-05 be split instead?
