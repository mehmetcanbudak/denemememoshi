# Slice A — Agent-driven declarative generative UI & streaming structured output into native views

Research date: **2026-11-11**. Scope: native Apple (SwiftUI/AppKit; iOS/iPadOS/macOS 27; visionOS bonus) for Memoshi.
Labels: **Observed** = read in the cited primary source today. **[INFERENCE]** = my reasoning. **[SECONDARY]** = only seen in a non-owning source.
Memoshi constraints applied: D53 (A2UI-style JSON cards vs ~25-block catalog), D68 (own Swift-subset interpreter), D80 (MLX Qwen3 1.7B/4B on device), FM for small jobs, no JIT / no child processes, A16 iPhone 14 Pro without Apple Intelligence.

---

## 0. TL;DR

1. **The biggest change for Memoshi is not a UI protocol; it is that Apple's `@Generable` / `streamResponse` path now accepts non-Apple models.** iOS 27 adds the public `LanguageModel` protocol. `MLXLanguageModel` (in `mlx-swift-lm`) conforms to it and does **grammar-constrained decoding through vendored XGrammar**. So Qwen3 on the A16 phone can feed the same `PartiallyGenerated` snapshot stream into SwiftUI that Apple's system model feeds. The phone has no Apple Intelligence, but that does not block this path. (Observed: Apple docs, WWDC26-339, mlx-swift-lm README.)
2. **A2UI v1.0 is now "Current"** (it moved out of Candidate on 2026-11-06). Google also shipped an **official SwiftUI renderer**, the A2UI Swift SDK 0.10.0 (iOS 17+/macOS 14+, Apache-2.0), and SwiftUI is in the cross-renderer conformance suite. The community renderers from August are no longer the only option.
3. **A2UI now separates the model's output format from the wire format.** "A2UI Express" is a Python-like positional DSL that a deterministic compiler turns into wire JSON. Google reports up to 3x fewer tokens and 3x lower latency (Observed, Google blog 2026-10-27). OpenUI Lang (Thesys) works the same way: it reports 96.9% structural validity using 52% fewer output tokens than A2UI JSON on its own benchmark. For a 15–20 tok/s phone, the token count largely sets the card latency.
4. **Small models fail free-form generative-UI output.** On the OpenUI benchmark, unconstrained LFM 2.5 2.6B scores 3.3% validity, Granite 4.1 8B 14.7%, and Ministral 8B 27.2% (Observed). [INFERENCE] On-device Qwen3 1.7B/4B will only work for D53 cards with **constrained decoding plus a compact format**.
5. AG-UI 1.0 (stable 2026-09-30) and MCP Apps (stable spec; ext-apps v2.1.0 shipped 2026-11-10) both matter for *remote* agents. MCP Apps renders only through HTML/iframe, which means **WKWebView only** on Apple platforms. Neither is on the critical path for on-device bots.

## 2. Candidate techniques (per-candidate tables)

### 2.1 Foundation Models guided generation + `LanguageModel` protocol (iOS/macOS 27)

| Field | Detail |
|---|---|
| What | Annotate Swift types with `@Generable` / `@Guide`, or build a schema at runtime with `DynamicGenerationSchema`, then call `respond(to:generating:)` or `streamResponse(...)` to get typed output. "The framework uses constrained sampling … prevents the model from producing malformed output" (Observed, https://developer.apple.com/documentation/foundationmodels/generating-swift-data-structures-with-guided-generation). Properties are generated **in declaration order**. Apple names "dynamically generating views at runtime" as a use case for nested Generables and enums with associated values (Observed, same page). |
| Streaming into SwiftUI | `streamResponse` yields **cumulative snapshots** of `T.PartiallyGenerated`, a mirror of the type with every property optional (Observed: Claude FM doc "Each element is a cumulative snapshot … not a delta", https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/apple-foundation-models; Apple ResponseStream.Snapshot doc). **`GenerationID`** is "guaranteed to be both present and stable" for the duration of a response. Apple's sample assigns `snapshot.content` inside `withAnimation` and uses `ForEach` with it as the identity (Observed, https://developer.apple.com/documentation/foundationmodels/generationid). |
| What's new in 27 SDK | Public **`LanguageModel`** protocol plus a **`LanguageModelExecutor`** that streams deltas through `LanguageModelExecutorGenerationChannel`. `LanguageModelCapabilities` include `.toolCalling`, `.guidedGeneration` and `.reasoning`. A request that needs an unsupported capability throws `LanguageModelError.unsupportedCapability` (Observed, https://developer.apple.com/documentation/foundationmodels/languagemodel, …/languagemodelcapabilities, …/languagemodelexecutor). The executor receives `request.schema` and has to honor it itself (Observed, WWDC26-339 code at 467–476: "Token budget too small to satisfy this schema"). Also new: `PrivateCloudComputeLanguageModel` (32K context, reasoning levels, needs an entitlement), `DynamicProfile`, `ToolCallingMode`, image attachments, `OCRTool`/`BarcodeReaderTool`, Spotlight RAG tool, Evaluations framework, `fm` CLI, Python SDK (Observed, https://developer.apple.com/documentation/updates/foundationmodels; https://developer.apple.com/videos/play/wwdc2026/241). Executors are cached per `Configuration` (Hashable); diff the transcript for KV-cache reuse; custom segments; metadata such as `tokensPerSecond` and `timeToFirstToken` (Observed, https://developer.apple.com/videos/play/wwdc2026/339/). |
| Non-Apple models on the same `@Generable` path? | **Yes.** Apple's lab answer: "this year's LanguageModel protocol lets you drive any model through the same unified Swift API for prompting, tool calling, and @Generable output … a custom provider … can serve a single LanguageModelSession across all devices", and an OpenAI chat-completions conformer ships in `foundation-models-utilities` (Observed, https://developer.apple.com/videos/play/wwdc2026/8016 at 58:52). Shipping conformers: `MLXLanguageModel` (§2.2); `ClaudeLanguageModel` (Apache-2.0, beta, uses Claude structured outputs for `@Generable`, v0.2.3 on 2026-10-07; https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/apple-foundation-models); Gemini through Firebase AI Logic `geminiLanguageModel(name:)` (preview; https://blog.google/innovation-and-ai/technology/developers-tools/bringing-gemini-models-to-apple-developers/). **Caveat:** each conformer implements constrained output its own way. MLX uses token masking, Claude uses server-side structured outputs. The guarantee is only as strong as the executor (Observed in docs; strength comparison is [INFERENCE]). |
| Maturity/date | Framework GA with iOS 26. The 27 SDK features shipped with the iOS 27 release (announced June 2026). Anthropic's package is still marked "beta" (Observed). |
| Apple path | `import FoundationModels`; iOS/iPadOS/macOS/visionOS 27 for `LanguageModel`. `GenerationID` and `DynamicGenerationSchema` exist since 26 (Observed, availability blocks). [SECONDARY] iOS 27 supports A13 and later, iPhone 14 Pro included (9to5Mac/Wikipedia). `SystemLanguageModel` stays unavailable on A16 because there is no Apple Intelligence. |
| On-device vs cloud | Any of: system model (not on A16), MLX/CoreAI local, PCC, Claude/Gemini cloud. |
| Measured numbers | Apple primary: iPhone 15 Pro ~0.6 ms per prompt token TTFT and ~30 tok/s (2024 model; https://machinelearning.apple.com/research/introducing-apple-foundation-models). [SECONDARY] iOS 27 system model at 56 tok/s on iPhone 17 Pro, TTFT 1.3 s (askloci.ai). **No primary A16 numbers exist** because there is no system model on A16. |
| License | Proprietary framework. utilities Apache-2.0; coreai-models BSD-3 (Observed). |
| Fit for Memoshi | **High.** One `LanguageModelSession` API for Pi_Swift bots across Mac (system/MLX/PCC), iPad M1 (MLX; system model if eligible) and iPhone 14 Pro (MLX only). `DynamicGenerationSchema` can be generated from the D53 catalog JSON at runtime, so the catalog itself becomes the grammar. Risks: FM requires the 27 SDK (Xcode 27.2 is fine); `@Generable` output is a typed tree, not A2UI flat-adjacency messages, so an adapter is needed (§2.6); the system model's 8,192-token context (Observed in the WWDC26-241 summary) makes a full ~25-block catalog schema expensive. |
| 1–3 day experiment | **E1 "Catalog→DynamicGenerationSchema stream".** Write a converter from the D53 catalog JSON to `DynamicGenerationSchema` (anyOf over block kinds, each an object with typed props, children arrays capped at depth 4). Stream 20 prompts × 3 models (system model on the Mac, `MLXLanguageModel` Qwen3-1.7B-4bit on the iPhone 14 Pro, Qwen3-4B on the iPad M1) into a SwiftUI card view keyed by `GenerationID`. Measure: schema-compile time, time to first rendered block, total time, % of outputs passing the D53 validator, dropped frames during streaming (Instruments). **Pass:** ≥98% validator pass; first block visible ≤1.5 s on the iPad and ≤2.5 s on the iPhone; no hitches >16 ms on the main thread. |

### 2.2 MLX Swift guided generation (`MLXFoundationModels` + `MLXGuidedGeneration`, XGrammar)

| Field | Detail |
|---|---|
| What | `MLXLanguageModel` is "analogous to SystemLanguageModel, usable directly with LanguageModelSession, so existing FoundationModels code (guided @Generable output, tool calling, streaming) works unchanged" (Observed, https://github.com/ml-explore/mlx-swift-lm/blob/main/Libraries/MLXFoundationModels/README.md). `MLXGuidedGeneration` constrains any MLX model to a **JSON Schema, an EBNF grammar, or an XGrammar structural tag** by masking logits at every step. It runs **standalone on macOS 14 / iOS 17+** (Observed, …/MLXGuidedGeneration/README.md). |
| Maturity/date | Added in PR #334 (merged 2026-07-15); released in **3.32.3 (2026-09-30)**. Repo is active (push 2026-11-11), MIT, 862★ (Observed, gh api). Default capability is `[.guidedGeneration]`; capabilities are declared, not inferred. The schema plus `@Guide` descriptions are injected into the system prompt unless `includeSchemaInPrompt: false` (Observed). |
| Apple path | SwiftPM `mlx-swift-lm` products `MLXFoundationModels`, `MLXGuidedGeneration`, `MLXLLM`, `MLXHuggingFace`. Trait `FoundationModelsIntegration` (on by default) needs the 27 SDK; disable it for the standalone engine. `#huggingFaceLanguageModel(configuration: LLMRegistry.qwen3_0_6b_4bit, capabilities: [...])` (Observed). XGrammar is **vendored C++ with a renamed namespace**, compiled AOT (Observed). That makes it compatible with no-JIT / no-child-process rules [INFERENCE]. |
| On-device | Yes (GPU via Metal). |
| Measured numbers | Repo ships `GuidedGenerationBenchmarkTests` (constrained vs unconstrained throughput, fast-forward effectiveness, grammar compile time) but **publishes no numbers** (Observed, test file). README warning: a cold grammar compile "can block for hundreds of milliseconds"; prewarm off `@MainActor` (Observed). XGrammar paper: up to 100x faster than prior engines, "near-zero overhead" end to end (Observed, https://arxiv.org/abs/2411.15100; server GPUs, not Apple). MLX decode throughput from a primary benchmark repo: Qwen3-0.6B at 178.8 tok/s on iPhone 17 Pro, warm, 128-token budget (Observed, https://github.com/john-rocky/apple-silicon-llm-bench, MIT). [SECONDARY, unverified] Qwen3-1.7B on iPhone 14 Pro runs at ~15–20 tok/s (promptquorum.com). **Memoshi must measure on A16.** |
| License | MIT (mlx-swift-lm), Apache-2.0 (XGrammar). |
| Fit for Memoshi | **Highest.** This is the only first-party-maintained path where D80 Qwen3 on the A16 gets *hard* structural guarantees *and* `PartiallyGenerated` streaming. EBNF support means a compact DSL (§2.4) can also be constrained, not just JSON. Risks: 6 GB RAM (4B-4bit is ~2.1 GB of weights [SECONDARY]); the 27-only adapter; grammar compile latency per catalog version (cache it); a token mask that is constrained but semantically wrong (valid but ugly cards); unpublished A16 performance. |
| 1–3 day experiment | **E2 "Constrained vs unconstrained Qwen3 on A16".** Using `GuidedGenerationLoop` directly (no FM dependency), run 50 card prompts × {Qwen3-1.7B-4bit, Qwen3-4B-4bit} × {unconstrained + prompt, JSON-schema constrained} on the iPhone 14 Pro and iPad M1. Measure validity (D53 validator), decode tok/s with and without the mask, cold and warm grammar compile ms, peak RSS (`os_proc_available_memory`), and thermal state after 10 runs. **Pass:** constrained validity 100% structural and ≥90% semantic (human spot-check of 20); mask overhead ≤15% tok/s; warm compile ≤20 ms; peak RSS ≤3.2 GB on the iPhone. |

### 2.4 Compact UI DSLs as the *inference format*: A2UI Express, OpenUI Lang

| Field | Detail |
|---|---|
| What | The model writes one statement per line, close to Python (`root=Card(main_column)`, `$/title="…"`, `Event("accept")`). A deterministic compiler, generated from the catalog schema, produces validated wire JSON, assigns deterministic IDs (`root_child_children_0`…), and heals open strings on `progressiveKeys` while streaming (Observed, https://a2ui.org/concepts/inference-formats/; https://developers.googleblog.com/fast-reliable-a2ui/). OpenUI Lang 1.1 has a formal EBNF, a streaming parser contract, built-ins (`@Count`, `@Filter`, `@Each`…), and `$state`/`Query`/`Mutation`/`Action` forms (Observed, https://github.com/thesysdev/openui/blob/main/spec/language.md). Google says Express was "inspired in part by OpenUI Lang"; the projects have proposed converging syntax (a2ui #3214; Observed in the blog). |
| Maturity | Express is the **default** inference format in the a2ui Python, TS and Dart agent SDKs (py 0.9.0 on 10-17 → 0.11.0 on 11-10). OpenUI: MIT, 15,086★, packages released daily (`@openuidev/*` on 11-10). Swift ports are toy-level (Observed). |
| Numbers | Google: Express needs "up to 3x fewer tokens" and gives "up to **3x** lower latency". A 4-format eval (Direct JSON, Express, Atom S-expr, Elemental HTML) over 51 tasks on gemini-3.5-flash found Express "works just as well even with thinking off". Jev decision-model path: tree on screen in 92–298 ms, complete in 0.8–1.7 s over 11 prompts (small sample, flagged by the authors) (Observed). OpenUI benchmark: **OpenUI Lang 96.9% valid / 99.9% render / 5,031 prompt tokens / 1,362 output tokens vs A2UI JSON 95.6% / 96.6% / 12,610 / 2,823** (Observed, first-party, so treat with care). |
| Apple path | No official Swift compiler for either. Options [INFERENCE]: (a) port the Express compiler, a few hundred lines of positional-arg → schema-order mapping, to Swift; (b) **reuse D68's SwiftSyntax front end**: define the card DSL as Swift-like constructor calls (`Card(Column([Text($title)]))`), parse with SwiftSyntax, and lower to D53 JSON, giving one parser for cards and mini-apps; (c) run the TS `@a2ui/agent` compiler in JavaScriptCore (works without JIT, but adds a second runtime; not recommended). Constrain the DSL on device with an **EBNF grammar through `MLXGuidedGeneration`** (Observed: EBNF is supported). |
| On-device | Yes (compiler + grammar). |
| License | A2UI Apache-2.0; OpenUI MIT (Observed). |
| Fit for Memoshi | **High for latency on the A16.** [INFERENCE] Arithmetic: with the benchmark's mean output (A2UI JSON 2,823 tokens vs OpenUI 1,362) at an assumed 15–20 tok/s on A16, a full screen takes ~140–190 s vs ~70–90 s. Memoshi cards are much smaller, but the ratio carries over, so a 600-token JSON card (~30–40 s) becomes ~200 tokens (~10–13 s). Risks: a second format to maintain; few-shot examples must be decompiled (the A2UI SDK does this automatically, Memoshi would have to build it); small models know Python and Swift syntax better than a custom DSL, which favors option (b). |
| 1–3 day experiment | **E4 "Swift-syntax card DSL vs JSON".** Write an EBNF for a Swift-call card DSL covering the D53 catalog, a SwiftSyntax → D53 JSON lowering, and run 50 prompts on Qwen3-1.7B/4B (constrained by the EBNF vs constrained by JSON Schema). Measure output tokens, wall time, validity, and a blind human A/B on card quality. **Pass:** ≥2x fewer tokens and ≥1.8x faster end to end at equal validity, with no quality loss (A/B ≥45% win or tie). |

### 2.5 Controlled / template generation with decision models (Jev "System One" pattern)

| Field | Detail |
|---|---|
| What | A decision model answers ~30 typed multiple-choice questions per screen from a Markdown grammar (archetype, row control kind…). Deterministic code builds the A2UI tree and sends `createSurface`/`updateComponents` at about 200 ms with placeholders, then a small LLM streams only the text into `updateDataModel` (Observed, Google blog 10-27; https://github.com/dglazkov/jev2ui Apache-2.0, 11★). |
| Numbers | Tree at 92–298 ms, complete at 0.8–1.7 s, 101–341 text tokens per screen, valid A2UI on 11/11 prompts. The grammar covers 9 archetypes and 12 blocks (Observed). |
| Apple path | Jev is a cloud product (TypeSafe). [INFERENCE] The *pattern* runs on device: use FM's system model or Qwen with `@Generable enum` choices (guided generation is ideal for classification), pick a template card, then stream text into its data model. |
| Fit | **High for recurring card types** (reminders, summaries, check-ins): first paint well under a second even on the A16, because only short enum decisions are decoded before layout [INFERENCE]. Low for novel mini-apps (D68 covers those). |
| Experiment | **E5 "Template-first cards".** For the 6 most frequent D53 card intents, define templates. Then: `@Generable enum CardTemplate` plus a slot struct, render the template skeleton immediately, and stream slot text. ## 5. Risks & open questions (cross-cutting)

- **Spec instability:** A2UI v1.0 is "current" yet had breaking changes on 11-03 and 11-11. Pin a commit and gate on the conformance fixtures (Observed churn).
- **Constrained ≠ good:** grammar masks guarantee shape, not layout quality. EvoGenUI shows multi-turn state drift even for frontier models. Card *updates* (data-model patches) are safer than regenerating whole trees [INFERENCE from Observed failure taxonomy].
- **A16 performance is unmeasured in primary sources.** Every latency budget above for the iPhone 14 Pro is an assumption until E2 runs.
- **FM open-source core not yet published** (Observed absence). Do not plan on reading FM's constrained-decoder source.
- **Security:** A2UI Swift SDK now gates local `functionCall` actions on user activation and restricts media URLs (Observed, #3821/#3766). Memoshi's D53 validator should mirror both. MCP Apps HTML must stay in a separate WKWebView trust tier.
- **Schema-in-prompt cost:** the system model has an 8,192-token context. Catalog schemas must be pruned per request (e.g., only the blocks relevant to the bot's profile), which DynamicProfiles can switch [INFERENCE].

## 6. Ranked shortlist (slice A, top 3)

1. **On-device grammar-constrained generation via the FM `LanguageModel` path (`MLXLanguageModel` + `MLXGuidedGeneration`/XGrammar), with the D53 catalog compiled to `DynamicGenerationSchema` or EBNF and `PartiallyGenerated` snapshots streamed into SwiftUI keyed by `GenerationID`.** One first-party-maintained API covers Mac, iPad and the A16 iPhone, and hard constraints are the only evidence-backed fix for small-model invalidity (3–28% unconstrained validity for ≤8B models).
2. **Align the D53 wire format with A2UI v1.0 and use the official A2UI Swift SDK 0.10.0 (`A2UISwiftCore` at minimum) as validator and state engine behind Memoshi's own SwiftUI catalog views.** It is now first-party, conformance-tested including SwiftUI, Apache-2.0, and gives free interop with ADK, AG2 and CopilotKit agents. Pin a commit until v1.0 freezes.
3. **A compact inference format (A2UI-Express-style, ideally Swift-call syntax parsed with D68's SwiftSyntax front end), constrained by EBNF on device and compiled deterministically to D53 JSON, plus template-first "controlled" cards for frequent intents.** Google and OpenUI both measured roughly 2–3x fewer tokens, which is the main latency lever at A16 decode speeds, and it unifies the card and mini-app parsers.
