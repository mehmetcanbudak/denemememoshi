## 4. Proposed decision updates

These are proposals only. No decision below has been taken unless [decisions.md][decisions] records it.

1. **[D135][d135] (decided 2026-11-14): row 5 keeps failing, with a named exception.** The `target=_blank` preconnect keeps S3 row 5 (06 row 6) failing; on 2026-11-14 it persisted with trusted native clicks, so a bot using real input does not avoid it. D101 already calls it "a known, retained failing control". The owner chose among the [Network Extension filter study][ne]'s options (§5) on 2026-11-14, and D135 records the result:
   - **A (taken).** Keep D101, report the gap to Apple and WebKit with a minimal reproduction, and record the preconnect in this report and the gate review as a named exception, not a pass. The residual is one empty connection to a host the page already named; no request, cookie or page data is sent.
   - **D (taken, later).** The gap closes when bots browse only inside their own Bot computers ([D113][d113]); until then bot browsing on This Mac carries this limit.
   - **B and C (not built now).** A Mac content filter needs the open signing work, a system extension the user must approve and an exception to 08 §15; it can be reconsidered if the upstream reports stay unanswered when Bot computers are planned. A filter would not help on iPhone and iPad (content filters there need supervised or managed devices).
   - **E (rejected).** A script click interceptor is not a boundary.

   No change to the threshold is made: row 5 is scored **fail** with the exception named. [R34][r34] lists "a threshold renegotiated after the fact" as a trigger.
2. **[D101][d101] consequence, Lockdown on real sites.** D101 records that real-site task success under Lockdown is unmeasured. On owned fixtures it was 6/8 on 2026-11-14 and 7/8 in three runs on 2026-11-16, with no run of the same suite without Lockdown to compare against. Proposal: the S3.3 corpus run is scored with Lockdown on, as the product would run. If it misses 90%, the owner decides between Lockdown and row 5, because [design §5][design] states that without Lockdown no public API closes WebRTC on macOS 27.
3. **[D136][d136] (decided and built 2026-11-14), private data and navigation.** On 2026-11-14 (run 1), a profile whose store held a non-probe cookie refused every cross-origin GET navigation, including the first load from a blank page, and no confirmation path exists for GET (`BrowserSessionReview.navigationDenial`). It failed closed ([README][nb14]). D136 replaces that refusal, and the change is built, reviewed three times and committed (`fabd26e`) ([D136 evidence][d136e]):
   - **Site rule.** A site is the scheme plus the registrable domain (eTLD+1) from a bundled Public Suffix List (publicsuffix.org snapshot of 2026-11-13, MPL-2.0, recorded in `NOTICE`). Grants and content rules stay per exact origin (D101); only the choice of profile uses sites. Since 2026-11-18 (`89ca9f4`), a site the bot is told to open uses the bot's own profile only when that profile has shown pages of that exact site, has not shown the same domain under the other scheme, and holds a cookie of that domain (`BrowserAuthorization.holdsCookie(of:cookieDomains:shownSites:)`). The shown sites are recorded at each main-frame commit in the bot's own profile, under `browser-review.shown-sites.<profile id>`, and deleted with the profile. So a domain shown under both schemes, and cookies planted outside the product, open in a separate profile. An IP address has no registrable domain (`PublicSuffixList.isIPAddress`) and is its own site. A site that cannot be read matches nothing, and configuration refuses when the Public Suffix List is missing (`publicSuffixListUnavailable`).
   - **Moves.** While the bot's profile holds private data, a move to another site, or a site the bot is told to open for which that profile holds no cookie, goes to a separate, throwaway profile with no cookies or storage, discarded when the task ends, under the bot's own gateway client, deny-local rules and Lockdown. A confirmed cross-site form opens there too (a POST with its body, or refused); `_blank` links and script moves are judged from their page; `window.open` stays refused. Rule lists left by a crash are swept at the next start.
   - **Return.** A top-level GET back to the site the bot's profile shows (a link back or an SSO-style redirect) returns to the signed-in profile and behaves like a normal browser's cross-site GET: Lax cookies are sent, Strict cookies withheld, `Sec-Fetch-Site: cross-site`. A POST back is refused. This is proven on the direct route at owned fixtures. On the gateway route the D136 run proves the lane and the route (the return's CONNECT reached the bot's gateway client, never a gateway of the separate profile). On 2026-11-21 the gateway scenario's return to plain-http `.test` hosts sent the Lax cookie, withheld the Strict one and sent only the origin as Referer, but carried no `Sec-Fetch-Site`, which WebKit sent on none of that route's requests (§1a); `Sec-Fetch-Site: cross-site` on the gateway route stays unmeasured.
   - **Final run** `control-d136g-6c65b0d938cf` ([summary][d136g]): 28/28 scenarios, exit 0, 0 unattributed, 0 sink events in every product scenario, every separate-profile fact true; `strictPass` false only for the `_blank` preconnect (D135). Owned loopback fixtures and `.invalid` names only; no `.local` positive; no real site. Under the 2026-11-18 analyzer it re-analyses as not passing, only because it predates the T10 crash fields and the edges scenario (§1a).
   - **Limits.** The Referer of a return is always the leaving page's origin, even when that page's policy is `no-referrer`. With JavaScript off in the bot's profile there is no return; the move stays in the separate profile. A crash with a separate profile open is covered by the sweep scenario, which kills a child with a live separate profile; it passed in the 2026-11-19 control and in the complete control of 2026-11-21 (`crashKilledWithLiveProfile`, `crashNoFilesLeft`; T10). Of the two gaps from the 2026-11-18 review, frame embedding reads the private-data flag from the profile's store since 2026-11-21; in lab browsing without the runner a separate profile still has no task end, an owner question (§1a).
   It bears on row 1, since a signed-in bot that could not follow cross-site links would fail tasks.
4. **The `.local` positive control: no longer owed.** The 2026-11-15 run `control-d136local-39e03b203c57` exercised both `.local` names ([README][d136e]). No Local Network prompt appeared: macOS attributed the carrier's request to its responsible process, the terminal app that launched the harness (`Tern.app`), which already held the permission. So this run alone does not explain the earlier `.local` timeouts [INFERENCE: probably a responsible app or session without the permission at the time]. A signed carrier would still make the attribution independent of the launching app; that matters for the reference-box and signed-build runs.
5. **New owner input, the real-site corpus.** Approve or replace the [corpus proposal][corpus] inputs U1–U10. Until that happens, rows 1 and 3 and the real-site part of row 5 cannot run.
6. **[D18][d18] and [D19][d19]: no change proposed.** Nothing observed contradicts them. Per-profile stores kept cookies apart across a relaunch, and moves into and out of the live view kept the same document.
7. **Fallback wording.** The draft said background browsing would wait for "Chromium with Bot computers in v1.1". [D113][d113] moved Bot computers to the end of Phase 2, and [phase-0 S3][p0s3] already says so. No further change is needed.
