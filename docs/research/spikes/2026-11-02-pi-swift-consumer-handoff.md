## 2. H1: durable waits and interrupted-step settlement (planned: P04-06, P04-07)

Memoshi does not re-request these work packages. It asks that their acceptance cover the observable behavior below, which its cards, events and recovery rules depend on.

### 2.1 Waits

1. **Kinds:** approvals (E6), ask-user questions and forms, a child's question to its parent, interrupted-step decisions (E20) and the provisional-runner authority wait of §3.3. One mechanism; the kind and a host-defined payload are visible to the host. Memoshi maps kinds to `waitingOn`: approval → `approval`; question/form → `user`; interrupted decision → `resume`; authority → `authority`. A running outcome check maps to `outcome_check`.
2. **Invocation-free and restart-stable:** a waiting task holds no tool invocation. Kills while waiting leave `restarts == 0` and do not repeat the hook's side effects (P04-06). After reopen, the same wait reappears with the same stable ID and payload in the snapshot and task graph, so Memoshi rebinds its existing card instead of creating a second one.
3. **Idempotent creation:** creating a wait is keyed by task plus a host-chosen key, so a deterministic hook that reruns after a crash finds the existing wait. `HookApi.memo` becomes public, as P04-06 plans; Memoshi then removes its `TaskRuntime` cast.
4. **Settlement:** `settle(waitId:value:requestId:)` with a host-defined JSON value. It returns `settled`, `alreadySettled(by:value:)`, `expired` or `notFound`. Two concurrent settles have one winner. The `requestId` is the client's original request ID, also when the answer arrives through `intent.forward` from another device ([D73](../../plan/decisions.md#d73)), so a repeated or forwarded answer cannot settle twice.
5. **Expiry:** the host supplies an absolute deadline in Unix milliseconds on the same clock as `HarnessOptions.now`. It is persisted and fires once on the engine clock across restarts. Approvals use D57/MASTER_PLAN §10 (30 minutes attended, 10 unattended, always 10 for T5); a card answered after its runner was unreachable past expiry is dropped, not applied (S2.9). Interrupted-step decisions have **no** expiry (02 §7.19).
6. **Cancellation:** stopping or aborting the owning task ends its waits as cancelled without running the tool. Memoshi marks the card `canceled`.
7. **Decision after settle:** the path that applies the settled value must not need the original invocation. The hook, or a designated continuation, observes the settled value exactly once per decision and can still block or allow. Dispatch-time re-checks stay with the host: Memoshi re-evaluates grants and mode when the call executes ([D79](../../plan/decisions.md#d79)).
8. **Nested calls:** a nested Code Mode or MCP call that waits behaves the same and reattaches after restart while the script replays from its journal (P04-03). Whether the VM stays resident during a long wait is SDK-owned; while resident it counts toward the Code Mode memory ceiling.

### 2.2 Interrupted steps

1. **Report:** after a restart or an expired lease, the host can read each interrupted call: task and call IDs, tool name, whether it was replay-safe, whether it never started (`cancelled`), started without a recorded outcome (`outcome_unknown`) or produced a late result, the recorded intent and arguments, and when it was cut off. Memoshi projects `tool.interrupted` and `Task.interruptedStep.since` from this.
2. **Outcome check (D51):** when the tool declares one, it runs automatically as a read-only call that gets the interrupted call's arguments and recorded intent, within its own timeout. It passes the mandatory policy like any other call (E21). It answers `happened`, `not_happened` or `inconclusive`; an interrupted check reruns, since it is read-only. `happened` records the step and continues; `not_happened` runs the step again under normal policy; `inconclusive` parks the task on an interrupted-step wait.
3. **Resolution through the wait:**

   | Memoshi action | Engine behavior required |
   |---|---|
   | Run again (`run_again`) | Re-dispatch the same call through the full policy path at current grants and mode, record a new intent, and execute with the **same task-derived idempotency key** (E20), so a keyed external API can deduplicate |
   | Skip (`skip`) | Do not execute. Commit a result that says the step was interrupted, when, and that the user skipped it, with a distinct diagnostic code; it reads as an error to the model |
   | Mark as done (`mark_done`) | Do not execute. Commit a result that says the step was interrupted, when, and that the user confirmed it happened, with a distinct diagnostic code |

   Every settled step's model-facing result says that it was interrupted, when, and how it settled: rerun, checked, run again, skipped or marked done ([D82](../../plan/decisions.md#d82)). The settlement records the action, the settling `requestId` and the actor, so Memoshi can emit `tool.outcome_checked` and `tool.interruption_resolved` exactly once.
4. **Hold:** while an interrupted step's check or decision is pending, nothing else in that conversation's store starts or resumes: no sibling, no unrelated child, no compaction, no inbox run ([D79](../../plan/decisions.md#d79), [D83](../../plan/decisions.md#d83)). The settle path itself (check, Run again) still runs. Memoshi keeps new user input in its own outbox meanwhile. Either the scheduler enforces this hold, or the SDK documents a primitive that lets the host resume only the settle path after an inspection-only open (paused scheduler) — Memoshi needs one of the two, stated in the consumer note.
5. **Never blind:** an unknown outcome is never retried automatically, and a "may have partially run" warning is not duplicate-effect prevention (P04-07's own wording).

### 2.3 Consumer acceptance Memoshi will run

On a pin that delivers P04-06/P04-07, Memoshi's adapter will exercise: 10 kills during a pending approval reattaching to the same card with `restarts == 0` and nothing executed before the decision; concurrent settles from two clients giving one winner and an `alreadySettled` answer; a settle after expiry returning `expired`; a stale forwarded answer dropped; an interrupted unsafe call taking each of `happened`, `not_happened`, `inconclusive` → Run again, Skip and Mark as done, each with the exact model-facing text and one event; the conversation hold observed while the decision is pending; and Run again reusing its idempotency key against an effect ledger. The [2026-11-03 authorization](../../plan/phase-0.md#team-and-calendar) releases owned synthetic **Mac** kill runs, not the missing SDK APIs, physical-device execution or reference qualification.

### 2.4 Consumer observation: nested-result retirement (2026-11-03)

This is a limitation of the **unchanged consumer pin**, recorded under H1/E20's interrupted-step/result contract and Memoshi's existing all-call audit/recovery acceptance. It is not a new request number, a new SDK filing, an SDK-source fix or a narrowing of S1.8/S1.10/S1.13. H4 in this record is already Code Mode.

**Source-backed failure window.** At `892585fc`, `Sources/PiDurable/Harness/ToolTask.swift` defines `nestedCallDoc` as a task-scoped `pi.tool.nested-call` family. `settleTool` writes the full `NestedToolExecutionResult` into the **parent task's** `NestedCallState.result`, while the completed nested task retains only `{"kind":"nested"}` in its terminal receipt, not an immutable result entry. The document retires with that owner; `Sources/PiDurable/Storage/SqliteStorage.swift` removes current-only document revisions on retirement. A process death after that retirement and before Memoshi has persisted its own authoritative completion receipt can therefore leave the completed task without recoverable result metadata. Parent success, a graph with no live node or an old `afterTool` observation cannot prove the nested call's actual final outcome.

**Current consumer behavior.** [`PolicyToolAudit.swift`](../../../Packages/MemoshiCore/Sources/Runtime/PolicyToolAudit.swift) captures content-free metadata synchronously from the live commit and drains it into immutable app receipts before publishing terminal facts. A committed app receipt deduplicates reopen correctly. That in-memory capture cannot close the crash window across separate stores: if the receipt is absent and the authoritative nested document is gone, reconciliation throws `projectionFailed`. [`RuntimeRPCError`](../../../Packages/MemoshiCore/Sources/Runtime/RuntimeRPCError.swift) maps the known refusal to safe `storage_failed`; Memoshi neither synthesizes `tool.completed`/success nor blindly re-executes an uncertain effect. Normal tools, MCP, Code Mode, environments and subagents remain `.none` in app/helper composition; trusted qualification opt-ins do not enable them in the product.

**Proof boundary.** Real foreground/background children and typed graph/history/targeted abort have [focused retained results](../../../../evidence/2026-11-03-memoshi-wave3-integration/native/runtime-child-conversation-tests.txt). [`SubagentKillResumeTests`](../../../Packages/MemoshiCore/Tests/MemoshiRuntimeTests/SubagentKillResumeTests.swift) SIGKILL an owned synthetic Mac host **after an immutable model-tool child checkpoint** and before the held child answer finishes; each case observes the same ownership, one `tool.completed` checkpoint and one effect after reopen. That is not a kill between nested-result retirement and app receipt. P0-15's `chaos` matrix has no wired nested Code Mode/child-retirement/compaction cut point. The parent's later [signed text-only protocol result](../../../../evidence/2026-11-03-memoshi-wave3-integration/native/signed-protocol-final/result.json) observes five-conversation SIGKILL/reconnect/original-receipt/history isolation through a normal no-tools helper; it does not exercise signed approval/card routing or this nested-retirement gap. Fresh S2 validation, full all-call audit/kill acceptance and the SDK H1/E20 recovery prerequisite remain open.

**What acceptance still needs.** At a qualifying SDK pin, retain authoritative completed nested-result metadata across owner retirement, or provide a durable host-consumption/acknowledgment contract that makes retirement safe. Then exercise the actual retirement-before-app-receipt cut, recover the exact final outcome/audit fact once, and verify no repeated effect. The SDK owns the API/storage design; this consumer observation does not select one.


## 3. H2: fencing and the host lease authority (planned: P04-05, P07-07)

E16's design notes already choose the checks: inside the local commit transaction, at replica ingest and in the hand-over handshake; the epoch rises on takeover only; the lease is revalidated at open before `resume()` and before effects. Memoshi asks that P04-05's interface and acceptance include the following.

### 3.1 What Memoshi supplies

A host authority object injected at open, behind which Memoshi runs CloudKit (`.ifServerRecordUnchanged` compare-and-swap) or the relay. It answers, for one conversation: the live epoch, the runner device, the lease expiry and whether the lease is **confirmed** or **provisional** (taken by direct hand-over without the authority, [D73](../../plan/decisions.md#d73)). Claims, renewals, releases, hand-over and `lease.fenced` stay Memoshi's protocol ([§12.6](../../specs/protocol.md#126-leases-and-hand-over)); epochs are monotonic `Int64` values per conversation, `expectedEpoch + 1` on a won claim.

### 3.2 Transaction fence

1. Each Pi commit carries the writer's epoch and is checked against the store's own fence record **inside the same SQLite transaction** (E16's `BEGIN IMMEDIATE` check). A stale commit is rejected whole and fails the Session; it never half-applies. A point-in-time check in another database, which is what Memoshi has today, does not satisfy this.
2. The host can **advance** a store's fence epoch at any time, for example on `lease.fenced`, a failed renewal or local expiry. The epoch never decreases, and every later commit with an older epoch fails. Renewal never changes the epoch.
3. At open, before any task resumes, the epoch is revalidated with the authority, because a restored or migrated device can bring a copy of the store: D79 excludes stores from device backups, and D80's exception includes them only for a sole device with iCloud and the relay off.
4. Replica ingest and the hand-over handshake reject stale epochs. A stale branch becomes a side thread (E19), not a merged history.
5. `FencedStorage` passes the storage conformance suite, keeps Swift-only tables in their own migration namespace, and leaves stores written by the previous pin readable (E23).

### 3.3 Effects

1. Before any non-replay-safe tool executes, nested calls included, the runner's lease is revalidated. A failure blocks the call before its intent is recorded, so no Resume card is manufactured for an effect that never ran.
2. A **provisional** runner may read, think and draft but runs no external effect until the authority confirms its lease. The call parks on the authority wait of §2.1 instead of holding an invocation, and resumes when Memoshi settles it.
3. Memoshi writes its `effect.intent` copy to another device or the relay before the effect, in the pre-effect host path ([D73](../../plan/decisions.md#d73)). The engine must give the host a point after policy and before execution where it can do this and may park on a wait.
4. After the local lease deadline passes without a successful renewal, no non-replay-safe tool executes until revalidation succeeds. Local lease time uses a monotonic clock (E16).

### 3.4 Feed and replicas (E17, P07-07)

Every delivered batch carries its commit `seq` and every snapshot, the overflow snapshot included, an `asOf`, so Memoshi projects each commit exactly once by storing the cursor in its own transaction. Replicas are read-only and accept external commits; promote performs the fenced hand-over. Memoshi's latest signed [consumer replay/rebuild proof](../../HANDOFF.md#consumer-follow-through-proof) exercised 1,000 reconnect cycles, 2,702 exactly-once applied/acknowledged facts, a fresh sequence-zero fold and ten helper EOF/restarts. Zero gaps/duplicates in that compared prefix proves its own event log, **not** this SDK feed or replication. The earlier 1,512-fact [foundation proof](../../HANDOFF.md#foundation-implementation-proof) remains historical.

### 3.5 Consumer acceptance

S2.5/S2.7/S2.10 and C21: stale-epoch writes rejected 100%; no two writers across 100 hand-overs; a provisional runner makes no external effect; a runner taking over after a copied intent runs the outcome check. These remain qualifying acceptance, not the current loopback prototype's verdict. The owned-Mac execution hold is released; SDK transaction fences, real Pi replication, physical devices and cloud authorities are still missing prerequisites. The [S2 command/proof boundaries](../../../Packages/MemoshiDaemon/Sources/MemoshiQualification/README.md#s2-durable-device-and-authority-qualification-prototype) record trusted host enrollment, reachable-relay dependence and the retained current failure; no new S2 pass is claimed.

## 4. H3: guarded file service inside `EnvDaemonSession` (new, untracked)

### 4.1 Evidence

- At the consumer pin, `Sources/PiEnv/Protocol/Daemon.swift` line 62 fixes `private let files = DaemonFiles()` and line 77 exposes only `public init(transport:)`. Neither file changed by SDK HEAD `f5dc5a1`.
- `DaemonFiles.dispatch` (`Sources/PiEnv/Protocol/DaemonFiles.swift`, lines 110–214) performs pathname operations: `write` creates parents and opens `O_WRONLY|O_CREAT|O_TRUNC` (or `O_APPEND`) without `O_NOFOLLOW`; `rename`, `rm`, `truncate`, `fsync`, `mkdir`, `mkdtemp`, `lstat`, `realpath`, `opendir`, `scanLines` and `listFiles` take paths; read-mode `open` follows links, and `noFollow` applies only to non-read opens.
- Memoshi's S4 runs found that preexisting hard-link aliases inside a grant reach outside inodes through raw reads, `RemoteExecutionEnv` file operations and SDK exec, under both Seatbelt designs and a separate user ([HANDOFF S4](../../HANDOFF.md#s4-confinement-kernel-gate), [separate user](../../HANDOFF.md#s4-separate-user-setup)). [D96](../../plan/decisions.md#d96) moves execution to private working copies but states that "the pinned SDK's missing guarded-file-service seam is not waived", and [D77](../../plan/decisions.md#d77) requires a daemon guard that resolves paths without following symbolic links. A host-side string check or transport precheck cannot make the daemon's later pathname operations race-free.
- The roadmap has no corresponding item: P06 covers export parity, peers, SSH, the official MCP runner, login-shell capture and kqueue; P07-03's descriptor-relative resolver is scoped to the iOS E9c filesystem.

### 4.2 Request

1. **A public seam.** A public protocol for the daemon's file operations and an `EnvDaemonSession` initializer that accepts an implementation. `init(transport:)` keeps `DaemonFiles()` as the upstream-parity default. The smallest acceptable shape exposes the existing dispatch boundary: `dispatch(_ request: JSONObject, payload: Data, context: Context) throws -> (JSONObject, Data)` plus `closeAll()`. A typed per-operation protocol is equally acceptable; the API design is the SDK owner's.
2. **Coverage.** Every path the daemon resolves goes through the injected service: all file operations, handle creation, and `watch` target resolution. `exec` and `pty` are out of scope; Seatbelt and private copies confine them.
3. **A descriptor-guarded implementation.** Either Pi_Swift provides one built on the P07-03 resolver, or Memoshi supplies it through the seam; Memoshi prefers the shared SDK resolver, so iOS and the Mac daemon do not grow two resolvers. Its policy inputs are host-supplied: root directories held as descriptors, read-only or read-write per root, and Memoshi's classification decisions. Its behavior:
   - resolve each component with `openat` and `O_NOFOLLOW` (or `O_NOFOLLOW_ANY` where valid), relative to a root descriptor, refusing any symbolic link and any escape from the root;
   - refuse regular files with more than one hard link and special files (FIFOs, devices, sockets) for reads and writes, as D96's admission does;
   - write atomically: a temporary file in the verified parent descriptor, then `renameat` into place ([D81](../../plan/decisions.md#d81)); never truncate a target in place;
   - keep `rename`, `rm`, `mkdir`, `mkdtemp` and directory listing inside the root, operating on verified parent descriptors;
   - bind open handles to their verified descriptors, so later `pread`, `writeChunk` and `fstat` cannot be redirected by a rename;
   - refuse writes under read-only roots, and report refusals with the existing wire codes (`SYMLINK`, `EACCES`, `NOT_REGULAR`, …) so `RemoteExecutionEnv` callers see ordinary errors.
4. **Conformance with the seam.** The upstream env file cases can run against a real daemon process configured with the injected service, beside the existing local and in-process lanes; HANDOFF records that the upstream fixture is currently hard-wired to local/in-process environments. Add escape, replacement-race and hard-link cases with independent expectations.
5. **Ownership.** Pi_Swift owns the seam, daemon wire semantics, conformance hooks and, if chosen, the shared guarded implementation. Memoshi owns roots, policy inputs, composition inside its sandboxed daemon entrypoint and the S4/D96 qualification evidence.

Needed by the gate pin freeze on Fri 2026-11-13 for S4 to qualify within Phase 0. Without it, S4/P0-12 stays open at the Fri 2026-11-27 gate and Memoshi's product file tools stay disabled; no date moves.
