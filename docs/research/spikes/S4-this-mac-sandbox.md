D96 stays authorized for development but not accepted; the stop rule holds CMP-03 and every ticket that runs bot commands or file tools; and the gate takes a new decision on D16. The Linux VM stays Linux-only and unqualified. Do not reopen the three rejected candidates: their failures were measured.
2. **Scoring the hard-link vector ([D137][d137], decided 2026-11-14).** On admitted copies, D96 refuses `st_nlink != 1` and late staged links (3 tests, 14 cases pass on 11-14), and H3's guard checks nlink ≤ 1. On raw fixtures, a path-based profile cannot deny the vector. D137 amends D96: a file that already has a second name on disk can be changed through that other name, and since admission refuses multiply-linked inputs such a file never enters a private copy; the 3 raw effects are recorded as an accepted limit, not a fail, and stay visible in every matrix run. The 0-escape bound is not lowered.
3. **[D103][d103] amendment.** Proposal, in three parts:
   - Record the 11-14 matrix result on the `d0dc184` profile.
   - Held-descriptor writes: decided by [D137][d137] (2026-11-14) as an accepted limit. A program that keeps a file open can write to it after export, and those writes land in the unlinked original and are lost (1,557 events in the final run); macOS offers no way to stop this. Before an export, Memoshi checks whether any process still has the file open for writing, waits briefly, and warns if one still does. Best effort, not a guarantee; the open-writer warning is built and committed (`71111a6`; [README][e14-attr2]). The whole check ends within 2 s, then the export applies as before; it sees only the user's own processes (no privileges), not memory mappings or a reopen after the check: the export tool's result carries `openWriters` data and a plain sentence that the model and the audit see; the Mac app has no export card yet, and that card shows the warning once it is built.
   - Multi-file exports are not atomic and end as `partialApplication`. Proposal: record this as an accepted, reported limit too, if the owner agrees; D137 does not cover it.
   - Record the 11-14 export change: objects are removed only inside a deny-ACL directory, and export refuses before any effect on volumes that do not report ACL support. Record its residual too: a process that rewrites that directory's ACL can still interfere. Since 2026-11-18 (`782caec`) export also refuses before any effect unless a probe directory shows that the deny entry is enforced (S4.3); the probe has not run on a real `-o noowners` HFS+ volume.
4. **Generic clients ([D81][d81], [D16][d16]).** Proposal: decide how proxy-aware toolchains reach the gateway. Installed Seatbelt rejects numeric host rules, and `localhost` admits the LAN, so the TCP allowance cannot return. The options to study are an in-sandbox Unix-to-proxy shim [INFERENCE], per-tool configuration [INFERENCE], or limiting Phase 1 to explicit clients. The phase-0 bound stays "every request reaches the policy engine".
5. **06 §12 row 7.** Proposal: state that Memoshi's profile has no `allowLocalBinding` option and no `network-bind` allowance, so the "with" half does not apply until a loopback dev-server need is decided. That need is 06's own fallback.
6. **06 §12 row 10 and [D77][d77].** The 11-14 per-invocation tag design is now the built attribution route, committed in `71111a6` ([attribution README][e14-attr2]). One Seatbelt instance per command is started by the unconfined host through PiEnv's `LocalExecutionEnv`, so D77's confined daemon no longer runs commands, only file operations; attribution needed no Pi_Swift/PiEnv request. No decision records this host-side route (commands through the host's `LocalExecutionEnv`, one `sandbox-exec` each); recording it under D96/D77 is a proposed decision awaiting the owner's decision ([HANDOFF, proposed decisions of 2026-11-18][h-proposed]). The route is what made the unconfined `cwd` lookup and the unbounded close possible (both fixed on 2026-11-18, see the introduction). A Pi_Swift request is proposed: `runCommand` should stop waiting on inherited pipes after a kill, abort or timeout once the leader has exited; today a detached child that keeps writing holds the call past its own `timeout`. The attribution rule: A denial is attributed to the command whose Seatbelt instance (process tree) produced it, by the tag the kernel prints. A detached child keeps its command's tag after that command returns; such denials are marked "after return". If a later command drives that child (through a shared file, FIFO or socket in the bot's home), the denial still names the earlier command; the later command's influence is not traceable from the report. Stated limits, after three review rounds: the kernel cuts reports at about 1,011 characters, losing the tag; since 2026-11-18 such a report is kept as unattributed "truncated" with its text only when every PID it names is Memoshi's, is ignored only when every PID is a live process of another app started before the monitor, and otherwise only counts in a `report_truncated` gap (S4.7). The log drops reports under load with no loss event (measured: 15,000 in 0.31–0.46 s delivered 5,242–9,652; paced floods lost reports at 1,000/s and above, depending on load). So ≥ 32 reports within 1 ms open a `report_burst` gap, ≥ 1,000 delivered reports within 1 s open a `report_rate` gap, and probes (4 reports each, every 100 ms while reports come fast, every 2 s while a command runs) grow a counted `reports_dropped` gap for each probe report that does not come back. A loss while fewer than 1,000 reports per second are delivered is seen only through a lost probe report. A Store or log that cannot keep up grows a counted `store_dropped` or `log_dropped` gap and refuses no command; only a command whose own invocation record cannot be written is refused. Counts are lower bounds. Proposal: record this rule and these limits with D77, and show a denial with no tag (truncated, or reported in a gap) as *unattributed*, never mapped to the active task ([draft §4d][draft-4d]).
